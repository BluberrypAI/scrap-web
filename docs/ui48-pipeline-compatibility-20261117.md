# 팀원 UI와 업체 검토 연결 수정

팀원 PR #48(`feat/47-ui-improvement`)의 디자인을 기준으로 연결 오류를 수정했다. 아래 기록은 최초 수정부터 PR 제출 전 최신 커밋 `3fb95e5` 통합까지의 검증 범위를 구분한다. GitHub의 PR #48을 대신 병합하거나 운영 배포하지 않았다.

## 수정한 부분

1. **물량 화면이 비는 오류**: `RecyclingTypes`를 사용하면서 import가 누락돼 브라우저에서 ReferenceError가 났다. import를 복구하고 실제 LotPanel을 렌더링하는 회귀 검사를 추가했다. 번들 빌드는 이 오류를 잡지 못했다.
2. **현재 보유 기업의 위치**: LotPanel이 서버의 `review.origin`과 `origin_label`을 후보 지도에 전달한다. B가 보유한 물량은 서버가 반환한 B의 위치를 사용한다.
3. **지도와 전체 목록**: 유효한 좌표·직선거리가 있는 가까운 최대 5곳만 지도에 표시한다. 목록과 AI 검토 대상은 줄이지 않는다. 5곳 밖의 업체를 명시적으로 선택하면 지도 5번째 자리에 표시한다. 검색·공정 필터는 지도에도 적용한다.
4. **새 소재의 형태 이름**: PS·EPS 등은 서버가 반환한 이름을 우선 표시한다. 이전의 고정된 이름 목록으로 되돌아가지 않는다.
5. **재검토 안내**: R유형 연결 이전의 검토도 재검토 안내를 보여 준다. 인수 요청의 기존 검증 조건은 그대로다.
6. **대기·미지원 문구**: 고정된 1~2분 보장과 PP·PE필름·알루미늄캔만 지원한다는 오래된 설명을 제거했다.

거리 미확인 업체를 가까운 업체로 간주하지 않는다. 이 지도 순서는 직선거리이며 실제 도로 운송거리 비교는 아니다.

## 검증

- Node 테스트 55개 통과. 실제 LotPanel 렌더, B 위치 전달, 서버 형태명, 기존 검토 안내, 후속 단계의 R유형 재확인을 포함한다.
- Vite 프로덕션 빌드 통과(275 modules). 기존 지도·3D 관련 500kB 이상 청크 경고는 남아 있다.
- 브라우저 합성자료 검사: 후보 8곳 목록 유지·지도 5곳, 8번째 업체 검색 후 1곳 표시, 보유 기업 B로 변경 후 B 위치·가까운 5곳 표시, 멀리 있는 업체 명시 선택 후 5곳 제한 유지.
- 브라우저 검사는 합성 기업·거리·물량으로 실제 UI를 렌더링한 것이다. 기업 로그인, 실제 지도 거리 계산, DB 저장, 수락·QR까지 검증한 결과가 아니다.

## 로그인 포함 통합 재검사 (2026-11-17)

Docker 통합 환경에서 별도 A·B·C 개발용 계정으로 PP 직접 완료(A→B, 펠렛 920kg), 중간 처리 후 완료(A→B→C, 파쇄품 950kg→펠렛 900kg)를 실제 웹으로 완료했다. 실제 문진·Azure 후보 검토·사진 업로드·조건부 수락·추가 자료·최종 수락·QR·완료·A의 재로그인 후 이력까지 확인했다.

이 과정에서 상단 단계 갱신, 수신/발송 기업의 카드 행동 안내, 업체 검색 시 다른 공정의 잘못된 빈 결과 표시를 수정했다. Node 테스트는 56개 통과했다. API·수락·QR 계약은 변경하지 않았다.

Google·Microsoft OAuth는 로컬 서버의 client ID/secret이 없어 검증하지 못했다. 시험용 업체 수락은 실제 허가·반입 승인 검증이 아니다. 자세한 결과는 scrap-server의 `docs/full-login-e2e-20261117.md`, 로컬 증빙은 `output/verification/full-login-e2e-20261117/`에 있다.
# 팀원 마지막 변경까지 반영

PR #48의 추가 커밋 `7848b5c`(인계 현황·근거·지도 화면)을 로컬 검증 브랜치에 병합했다. 기존 가까운 5곳 지도/전체 후보 검토, R유형 체크섬, 현재 보유 기업의 위치·서버 형태명, 발송자/수신자 안내를 유지했다.

- 완료한 공정을 다음 업체로 중복 표시하지 않는다.
- 입고 대기 안내는 발송 기업이 아니라 수신 기업을 표시한다.
- QR을 놓을 헤더 영역이 아직 없어도 원래 위치에서 발급할 수 있다.
- 웹 자동 검사 최종 61개 통과. 조건부 자료 제출·수락 뒤 QR·처리 중 실제 산출물 입력·완료 뒤 근거 조회의 렌더링 회귀 검사 포함.
- 로그인부터 두 PP 경로를 직접 클릭한 검사는 이전 UI 배치에서 완료했고, 이 변경 뒤에는 동일 실제 기록의 새 인계/확인사항 화면을 브라우저로 추가 점검했다. B 950kg·C 900kg, 2곳의 인계 지도, 완료 근거 번호를 확인했고 콘솔 오류 0개였다. 같은 결과를 모든 UI 버전의 전체 재실행으로 표현하지 않는다.
- 물량·확인사항 탭에서 완료 업체·용도·완료 근거 번호를 계속 볼 수 있도록 완료 카드를 유지했다.

## PR 제출 전 추가 통합

팀원 PR #48의 `3fb95e5`까지 반영했다. 새 알림함, QR 확대·링크 복사, 산출물 입력 오류 안내, 이전 처리 업체 중복 제거를 유지했다. QR은 팀원의 최신 배치대로 인수 요청 카드에서 발급하며, 별도 헤더 영역에 의존하던 코드를 제거했다. 등록 안내는 등록 직후에만 표시하고 현재 보유 기업 위치·전체 후보 검토·완료 근거는 계속 보존한다.

- 최종 Node 자동 검사 **63개 통과**, Vite 프로덕션 빌드 통과(280 modules). 지도·3D 번들 크기 경고는 남아 있다.
- 추가 통합 후에는 자동 검사·렌더링 회귀 검사·빌드를 실행했다. 로그인부터 두 PP 경로를 다시 전부 클릭한 결과로 표현하지 않는다.
- 병합 순서: **팀원 PR #48 → 이 수정 PR**. develop 대상 PR에는 #48의 커밋도 포함되므로, #48 병합 후 남은 변경을 리뷰한다.


## 최신 코드에서 새 문진으로 전체 재시험 완료

2026-11-17 후속 시험에서는 #48 최신 `3fb95e5`가 통합된 코드로 **새 PP 문진 두 건**을 만들었다. 별도 개발용 기업 계정으로 문진 → 사진 → Azure 업체 검토 → 수락 → QR → 산출물 → 완료를 다시 전부 눌렀다. 이전 문단은 과거 실행 기록이다.

- A→B 직접 완료: 1,000kg → 펠렛 920kg.
- A→B→C: 1,000kg → B 조건부 수락·자료·최종 수락·QR → 파쇄품 950kg → 새 사진·B 위치로 C 검토 → C 수락·QR → 펠렛 900kg 완료.
- 두 단계의 공정·업체 조합 14/14와 9/9 실제 AI 검토 완료. 검토 완료와 반입 승인은 구분한다.
- 서버 재시작 후 A 계정으로 두 완료 기록을 확인했다. 입고량을 넘는 산출물은 웹에서 차단됐다.
- 서버의 선택적 카카오 도로거리를 표시·정렬한다. 도로거리와 미확인 직선거리를 섞어 순위를 매기지 않는다. 지도만 최대 5곳이며 후보 전체 목록·검토는 유지한다.
- 후보별 완료/미완료 수와 실패 후보 재시도 안내를 추가했다. 표시·도로거리 변경을 포함해 Node **66개**와 Vite 빌드가 통과했다.
- 길찾기 키가 없어 실제 화면은 직선거리로 표시했다. 도로 응답·정렬은 모의 시험이다. 소셜 로그인·모바일 QR 카메라·실제 업체 허가는 미검증이다.

새 lot·사진 출처·증빙·수정 내역은 [최신 통합 보고서](https://github.com/BluberrypAI/scrap-server/blob/fix/e2e-release-20261117/docs/final-integrated-e2e-20261117.md)에 있다. 모든 소재가 완료됐다는 뜻은 아니다.
